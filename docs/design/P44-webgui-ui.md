# P44: the CobbleTowers web UI (production build)

Status: draft (2026-10-12). Replaces the mockup in `cobbletowers-ui.zip` as the real screen layer. Goal (owner): every CobbleTowers screen is a WebGUI page, to a high visual standard and fast in Rinku's Chromium, so no client jar is needed (P43).

## What exists
- The Java bridge (`webgui-bridge.md`): payload -> `emitToPage("tower", {kind, data})`, page actions -> the same handlers. Kinds already routed: IntermissionState, RentalDraft, RewardReveal, ScoutingReveal, VendorCatalog, TowerHallState, PlayState, MasteryScreen, TrackState, RunEffects.
- A mockup (one 73 KB `template.html` + `tower-bridge.js`): good art direction (warm pixel kit, Byzantine cards), but a single file with invented data and no structure. It is the visual reference, not the code base.
- Not routed yet: RegistrationState (party chooser), SpectatorPanel, TowerFeatureState (features), ArmorSets, ScoutingReveal page.

## Architecture
- **Sources** in `web/` at the repo root: `web/src` (ES modules), `web/assets` (textures, font, sprite atlases), `web/test`.
- **Runtime**: Preact + htm (vendored, ~6 KB), no router. One `app.js` and one `app.css` bundled by esbuild (`web/build.mjs`, node 20, the only dev dependency). Output goes to `src/main/resources/web/cobbletowers/` and is committed, so the jar carries the UI.
- **Delivery**: on server start the mod copies the bundled files to `config/webgui/web/cobbletowers/` when the stamped version differs. Installing the jar is the whole install.
- **State**: one store keyed by payload kind. A payload replaces its kind's slice; components subscribe to slices, so a tick of one kind repaints only what reads it.
- **Screens** are components chosen from the newest "screen-owning" payload (the rules in `webgui-bridge.md`: REPLACE kinds win, update-only kinds never open a page). The HUD page (`#hud`) mounts only the run overlay and ignores every other kind.
- **Actions** go through one `act(kind, fields)`; the page shows no optimistic state, the server's reply is the truth. Server refusals (chat messages today) are surfaced as toasts: needs a `Notice` kind (small Java addition).

## Design system
- Tokens (colour, spacing, type scale, z-index) in one CSS file; the 9-slice kit (`border-image-slice: 13` at 2x), Pixelify Sans with digits and ligatures handled as in the mockup notes, `image-rendering: pixelated`.
- Components: Panel, Button (4 states), Tab, Chip, CurrencyAmount, ModifierCard, RelicBadge, RentalCard (Byzantine), ProgressTrack, Toast, Modal, Tooltip (hover tooltips were owner-deferred; the web makes them cheap).
- Keyboard: Esc closes (WebGUI handles it), Tab order and Enter on focused buttons; Hall hotkeys optional.
- Accessibility floor: real `<button>`s, visible focus, no information by colour alone (benefit/cost keep the +/- sign).

## Performance rules (Rinku/CEF, one machine-wide cache, players on modest GPUs)
- Assets: sprite atlases for the 87 partner sprites, card fields/frames, gems, item icons; target under 60 files and 600 KB total (WebGUI limits 170 files / ~480 KB seen).
- Animate only `transform` and `opacity`; `contain: layout paint` on panels; no layout reads in loops; `will-change` only during a transition.
- Long lists (achievements, leaderboards, vendor) are windowed; payload over 32 768 chars is dropped by the bridge, so Mastery leaderboards page from the server.
- Budgets: first paint under 150 ms after `hello`, a state update under 8 ms of script, steady idle at 0 timers except the 1.5 s heartbeat. Measured with a headless-Chrome trace in `web/test/perf.mjs` against the fixtures and on the real client with `performance.now()` marks reported to the server log.

## Testing
- Node unit tests for the store/reducers and each screen's view-model (pure functions from payload to props), run in `ci_local`.
- Visual regression: headless Chrome screenshots of every screen from fixtures at 2 viewport sizes (1280x720, 1920x1080), diffed against committed baselines.
- Real client: the existing client-verification rig plus the testserver-webgui rig, with two clients for shared screens (Intermission, Lobby).
- Fixtures stay generated by `PayloadJsonTest`, so a payload change breaks the UI test, not the player.

## Build order (each slice ships, tested live, before the next)
0. Foundation: tooling, tokens, components, store, bridge, jar delivery, HUD page. Port Intermission, Rewards, Vendor and Rental Draft off the mockup onto it (they already work live), so nothing regresses.
1. **Hall** (TowerHallState) and **Briefing** (PlayState): the lobby path, since every run starts there.
2. **Run** screen and the in-run HUD (PlayState + RunEffects), replacing the K overlay: open by `/tower run`, a Hall button, and an item use (K replacement, owner to choose).
3. **Mastery** (MasteryScreen, TrackState): season, achievements, contracts, armory, leaderboards (server-paged).
4. **Registration** (party chooser), **Spectator**, **Feature** screens, scouting reveal; each needs its state kind routed in `ClientUi`.
5. Polish: sound (WebGUI audio permitting), transitions, hover tooltips, empty and error states.
6. Remove or gate `src/client` (end of P43).

## Decisions taken here (override if wrong)
- Preact + htm over a hand-rolled renderer or React: small, fast, no JSX build needed.
- UI sources live in this repo; the zip's `index.html` is retired once slice 0 lands.
- English only, strings from one table (`web/src/text.js`), so a language pass is possible later.

## Open
- K replacement (command, Hall button, item use: all three are cheap, the default is all three).
- Whether the bundled UI may also be served outside the jar (a `config` override folder for live editing during development: yes, in dev only).
